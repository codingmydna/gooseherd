### 1. Building verification loops in Claude Code with skills
[claude.com/blog/building-verification-loops-in-claude-code-with-skills](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills) — Claude Code team, 2026-07-22

**Pattern:** Verification loops come in four shapes — standalone (deliberately invoked, for cross-cutting checks like a pre-commit security scan or accessibility audit), embedded, chained, and PR-tied. The concrete `/verify` skill runs six phases (build, typecheck, lint, test+coverage, security scan, git diff review) and emits a pass/fail report. Two newer verification modes: spec validation (diff a change against a markdown spec file in the repo) and rubric grading (a separate, lightweight **grader agent** in Managed Agents, beta, scores an outcome against a rubric). The same skill wires into GitHub Actions to run on every push/PR.

**Parity impact:** Sharpened the existing "Verification skills" row (`docs/parity.md` §2) and added a new row for rubric-graded verification via an independent grader agent (gooseherd: ❌ — the `/orch` reviewer is rubric-injected but is the same role that also holds planning context, not a separate grader). Also surfaced that gooseherd has no GitHub Actions recipe for running its own gates/orch verification on a *target* repo's CI — confirmed by checking `.github/workflows/`, which only covers gooseherd's own source.

### 2. The new rules of context engineering for Claude 5 generation models
[claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models) — Claude Code team, 2026-07-24 (alongside the Opus 5 launch)

## Pick of the week

**Add a hard per-session subagent/delegate-call cap, mirroring Claude Code's `CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION`.**

Ready-to-run `/orch` task:

> Add a `GOOSE_MAX_SUBAGENTS_PER_SESSION` limit (default 200) enforced in `handle_async_delegate` (`crates/goose/src/agents/platform_extensions/summon.rs`), as a monotonic per-session counter separate from the existing concurrent `GOOSE_MAX_BACKGROUND_TASKS` cap — once the limit is hit, further delegate calls return an error explaining the cap and how to raise it via the env var, instead of silently continuing. Requirements: (1) the counter never resets mid-session and is independent of how many tasks have completed; (2) default 200, override via `GOOSE_MAX_SUBAGENTS_PER_SESSION`; (3) existing sessions with fewer than 200 delegate calls see no behavior change. Done when: a unit test simulates 200 successful `handle_async_delegate` calls followed by a 201st that returns the capped-out error (not a panic, not a silent no-op), a second test confirms an unset/default env var still allows exactly 200, and `cargo fmt`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test -p goose --lib` all pass.

Success criterion: **201st delegate call in one session is rejected with a clear error; the 200th still succeeds; `cargo test -p goose --lib` green.**
