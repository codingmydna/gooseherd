### 2. How Block orchestrates Claude Fable across thousands of pull requests — [post](https://claude.com/blog/how-block-orchestrates-claude-fable-across-thousands-of-pull-requests) (2026-10-08)
Block's internal usage: Fable plans (data models, API specs, algorithms) and "directs up to
dozens of smaller, more cost-effective models like Opus or Sonnet" to make edits and run tests,
across hundreds/thousands of PRs and multiple repos. A human steers; two humans approve every
deploy; agents run recurring daily/weekly passes across a whole codebase for cleanup work.
Notable line: "Fable on low might just be better than another model on xhigh" — i.e. effort
level is treated as a tunable dimension in the model-mix, benchmarked like a model choice.

**Pattern:** production-scale validation of (a) frontier-plans/cheap-models-implement, (b)
mandatory human gates on anything that reaches production, (c) recurring scheduled codebase-wide
agent passes, (d) effort level as a first-class axis in cost/quality tradeoffs.

**Parity impact:** This is real-world proof that gooseherd's founding premise works at scale —
good validation, no status change needed there. It does raise the priority of the **Proactive
loop** gap (still ❌): Block's "daily/weekly passes across a whole codebase" is exactly that
pattern, now shown to be worth having, not just a CC feature. Also strengthens the **Pilot run
before scaling** note under Cost observability with the effort-as-tunable-dimension point.

### 3. Automating eval design and hillclimbing with Claude — [post](https://claude.com/blog/automating-eval-design-and-hillclimbing) (2026-10-07)
Two new `/claude-api` skill commands: `build-eval` interviews the user and generates a scored
eval set inside the codebase; `hillclimb` then iteratively changes the target application/skill,
keeping a change only if the eval score improves and reverting if it doesn't — critically, it
holds out a validation slice the hillclimber never reads during training, and reverts any change
that only helped the visible (train) split, to catch overfitting to the eval itself. Reported
results include a support eval that got both more accurate and ~5x cheaper per ticket, and
Anthropic's own API skill improving from ~66% to ~88% accuracy through this loop.

**Pattern:** a generalized "generate-eval → hillclimb-against-it → held-out overfitting guard"
primitive, decoupled from any specific application — this is a different mechanism from gooseherd's
existing hill-climbing.

**Parity impact:** gooseherd has a feature that is also called "hill-climbing"
(`crates/goose-cli/src/session/exemplars.rs`, fed by `/arena` winners) but it only curates which
past-transcript *exemplars* get injected into plan/review prompts — it does not generate a scored
eval, does not iterate the *target implementation* against one, and has no held-out-slice guard
against the reviewer (or exemplar selection) overfitting to whatever test cases happen to be
visible. `/orch`'s only stopping signal today is the reviewer's qualitative VERDICT. **This is
this week's pick — see below.**

## Pick of the week

**Highest-leverage gap: no generate-eval-then-hillclimb loop with a held-out overfitting guard
for `/orch` tasks.**

Ready-to-run `/orch` task description:

> Add a `goose orch --hillclimb <n>` mode: before the first implement cycle, have the planner
> generate a small scored eval for the task (a set of concrete check cases derived from the task
> description plus existing tests, each with a pass/fail or numeric score), holding out 20% of
> the cases as a validation slice never shown to the implementer or reviewer during the cycle
> loop. After each implement→gates→review cycle, re-run the full eval; keep the cycle's changes
> only if the visible-split score improved, and separately check the held-out score — if the
> held-out score regressed while the visible score improved, flag it as likely overfitting and
> revert that cycle automatically rather than accepting it. Success criterion: on a seeded test
> task with 10 eval cases (8 visible, 2 held out) where a planted "cheat" fix only satisfies the
> 8 visible cases, `goose orch --hillclimb 10` detects the held-out regression and reverts,
> finishing with the held-out score unchanged or improved — verified by a new integration test
> in `crates/goose-cli/src/session/orchestrate/` asserting the final diff does not contain the
> planted cheat.
