## Pick of the week

**Fix `/stats`'s `/loop` aggregation so it breaks out tokens and run count per distinct loop task, not per role.**

Right now every `/loop` iteration is written to `orch_ledger.jsonl` with a hardcoded `role: "session"` (`crates/goose-cli/src/session/looping.rs::append_loop_ledger`), and `/stats` (`crates/goose-cli/src/session/ux.rs::handle_stats`) aggregates by `role · provider/model`. Run two different `/loop` tasks against the same model today and `/stats` reports them as one indistinguishable blob — you can't tell which loop is burning tokens. Claude Code's v2.1.243 solved exactly this by breaking its `/usage` loops view out per loop.

Ready-to-run `/orch` task:

> In `crates/goose-cli/src/session/looping.rs` and `crates/goose-cli/src/session/ux.rs`, change `/loop`'s ledger records and `/stats`'s aggregation so that runs from different `/loop` invocations are grouped separately instead of collapsing into one `role: "session"` bucket. Use the existing `run_id` (and/or the first `task_preview` seen for that `run_id`) as the grouping key for `/loop` records specifically, while leaving `/orch`/`/goal` aggregation by `role · provider/model` unchanged. `/stats` output for a session with two different `/loop` tasks against the same model must show two separate line items, each with its own run count, total tokens, and last-run timestamp — not one merged line.
>
> Success criterion: a new unit test in `crates/goose-cli/src/session/looping.rs` (or `ux.rs`) that appends ledger records for two distinct `/loop` run_ids against the same role/provider/model, calls the `/stats` aggregation logic, and asserts the result contains **2** distinct entries (not 1) with correct per-entry run counts and token totals. `cargo test -p goose-cli` passes.
